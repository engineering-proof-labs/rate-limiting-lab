## 1. Overview & Verification Principles

This document maps every technical capability and architectural claim made across the repository to:

1. **Concrete Implementation Path:** The exact source file and class/method responsible.
2. **Automated Test Path:** The deterministic unit, contract, or integration test proving the behavior.
3. **Reproducible Command:** The exact terminal command required to execute and verify the claim independently.
4. **Verification Evidence Status:** A strict distinction between verified implementation evidence and documented theoretical design.

## 3. Scope Boundary Declarations

To preserve absolute engineering transparency, the following distinctions govern all documentation and public references:

1. **Implemented vs Documented Design:** Claims 01–14 and 17–20 represent working, fully tested source code in this repository. Claim 15 documents a manual, agent-reported controlled mutation experiment rather than an automated CI mutation suite. Claims 21 and 22 (Scenarios 05 and 06) represent documented architectural designs and threat models; no production multi-region cluster or dynamic database synchronizer is implemented or claimed.
2. **Primary Node Atomicity vs High-Availability Durability:** The distributed limiter proves atomic admission on a single active Redis primary instance via single-threaded Lua scripting. It eliminates in-memory race conditions, but does not claim failover durability across asynchronous Redis replica nodes.
3. **Key Expiration Behavior:** Redis key expiration via `PEXPIREAT` is set to the exact epoch boundary `(windowId + 1) * windowMs` without a configured safety buffer.
4. **Memory Cardinality:** In Sliding Window Log, each individual client log is bounded by the limit since rejected requests are not stored; however, total memory consumption scales with the cardinality of distinct active client keys ($O(K \times L)$) and is not globally bounded without an active key eviction or TTL policy.
5. **Multi-App Concurrency vs OS Multi-Process:** Claim 04 tests two independent Express application instances with separate Redis TCP connections within a single Node.js process; it is not an OS-level multi-process or multi-host cluster test.
6. **Simulated Outage Recovery vs Live Failover:** Claim 08 tests self-healing recovery via an injected wrapper that toggles an error flag, rather than physical network disconnection or Redis primary failover.
7. **Local Closed-Loop Latency vs Production Throughput:** HTTP Supertest benchmark numbers (381 req/sec over loopback) measure unpipelined, ephemeral-socket client latency on a local workstation. They do not represent the upper network capacity of Redis (which exceeds 80k+ ops/sec via pipelined commands) or production Express deployments behind reverse proxies.
8. **CI Status:** The GitHub Actions workflow ([`.github/workflows/ci.yml`](../.github/workflows/ci.yml)) is verified against local Docker Redis, but remains unexecuted on GitHub's remote runners until code publication occurs.
